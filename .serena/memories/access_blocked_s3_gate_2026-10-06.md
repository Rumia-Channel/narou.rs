# Access-blocked S3 gate (2026-10-06, user decision)
- Symptom: every develop push failed the `Deploy Worker (develop)` job with `S3 verification failed (HTTP 403)`. Runs 37164602466 / 37410405076 / 37410535377.
- Cause: the Worker is deployed to a custom domain only (`workers_dev = false` because `DEVELOP_DOMAIN` is set), the app sits behind Cloudflare Access, and `NAROU_AUTH_REQUIRED=false` (CloudFlare environment variable) so the Worker itself has no Bearer gate. The mandatory probe therefore needs an Access service token, and `CF_ACCESS_CLIENT_ID` / `CF_ACCESS_CLIENT_SECRET` are not configured in the `CloudFlare` environment.
- Proof that 403 means "never reached the Worker": `GET /api/storage/mode?probe=s3` answers 503 for a failing S3 LIST (`worker_entry/src/storage_probe.rs`) and 401 for auth failures; the Worker never answers 403 on that route (the only 403 in `worker_entry/src/lib.rs` is cross-origin `POST /api/auth/login`).
- Decision (user, 2026-10-06): treat an edge 403 as a `::warning::` skip — `ci/deploy_worker.py` raises `AccessBlocked`, `verify_s3` returns `skipped: blocked before the Worker (Cloudflare Access or WAF); not verified`, and `summary()` prints that status. Success is never claimed. 401 / 503 / unreachable / invalid payload still fail the job.
- Setting the service token (`secrets.CF_ACCESS_CLIENT_ID` / `CF_ACCESS_CLIENT_SECRET` in the `CloudFlare` environment, plus a Service Auth policy on the Access application) restores the full verification; the plumbing (`probe_headers`, workflow env, `contract.mjs`) already sends the two Access headers.
- Tests: `worker_entry/tests/test_deploy_s3_contract.py` (`ProbeTests.test_access_blocked_probe_skips_with_a_warning`, `DeploymentFlowTests.test_access_blocked_deployment_completes_as_skipped`, `test_unreachable_deployment_is_not_skipped`). Policy text lives in `AGENTS.md` (S3 必須配備) and `docs/cloudflare-workers-migration-plan.md`.
