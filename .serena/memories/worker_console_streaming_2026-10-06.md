# Worker console streaming (2026-10-06)
- Symptom: on the Cloudflare build the Web console showed a download's per-section progress lines only after the job finished. `PushHubSink::emit` only buffered the lines and `drain()` ran once at the job boundary (`worker_entry/src/executor.rs`, `worker_entry/src/convert.rs`), so every line the downloader emitted per section (`src/downloader/mod.rs` → `report_line`) arrived at the end.
- Fix: `emit` now pushes into `narou_rs::application::messages::flush::FlushQueue` and starts one sender task (`wasm_bindgen_futures::spawn_local`) that takes the buffered lines and POSTs them (`broadcast_best_effort`) while the job runs. The queue owns FIFO order, the no-loss protocol around `finish()` (a line pushed while the task is finishing is picked up by the same task or starts a new one), and a 150 ms minimum send interval (`DEFAULT_MIN_INTERVAL_MS`) so bursts do not become one POST per line. Every POST counts against `SubrequestBudget` (`JOB_SUBREQUEST_BUDGET = 850`), which is why the interval throttle exists.
- `drain()` still runs at the job boundary but now waits (10 ms poll, at most 500 ms) for the in-flight sender before sending the remainder, so console lines always precede the job's terminal event.
- Tests: `cargo test -p narou_rs --lib application::messages::flush` (coalescing, no-loss protocol, FIFO across batches, throttle math). The wasm glue mirrors `HubProgress`, which already streams `progressbar.*` events the same way. Local `wrangler dev` verification is not possible in this sandbox: `cargo install worker-build` fails with schannel `SEC_E_NO_CREDENTIALS` (cargo cannot reach crates.io), so end-to-end observation has to come from the deployed Worker.
